# Seoul DEV authentication and routing handoff

This is a source and evidence map, not an assertion of current live configuration. The local checkout is platform-services `9f04f44e5dfc88272fcf380f96524f5bfdc92b75`; later candidate behavior below is identified by fixed source SHA. Check deployed image digests, effective task configuration, network paths and current release records before operating on DEV. Never record tokens, passwords, service proofs, or secret values in evidence.

## Request path and trust

In the checked-out [Gateway routes](../../gateway-app/src/main/resources/application.yml), `/api/v1/auth/**` goes to `PLATFORM_GATEWAY_AUTH_URI`, `/api/**` to Carelog, and `/rag/**` to Carelog RAG. The Kakao authorization and exchange POST routes have higher precedence and rate limiting. The [local topology](../../README.md#local-topology) defaults the auth upstream to Carelog when the explicit auth URI is unset; switching to Core also requires enabling Identity and supplying its runtime configuration. A source default does not establish the selected DEV upstream.

The [Gateway JWT filter](../../gateway-app/src/main/kotlin/com/ranikunlabs/platform/gateway/filter/JwtGlobalFilter.kt) blocks public access to `/api/v1/internal/**`, removes client-supplied identity and service headers, verifies protected bearer tokens, checks the blacklist, and supplies trusted claims and the Gateway secret to the upstream. Public requests receive sanitized headers. The upstream must be reachable only through an appropriately protected trust boundary; header removal at Gateway alone does not protect a directly accessible upstream. Identity logout independently derives the account from the verified bearer subject, not a client-provided user header; see [security tests](../../platform-core/identity/src/test/java/com/ranikunlabs/platform/identity/adapter/http/IdentityHttpSecurityConfigurationTest.java).

The later [Finance Gateway filter at candidate `f9adfd3d`](https://github.com/ranikun-labs/platform-services/blob/f9adfd3d338f482e7c2967512522e5b4e2354619/gateway-app/src/main/kotlin/com/ranikunlabs/platform/gateway/filter/FinanceTrustedContextGatewayFilter.kt) applies to its explicitly supported journal routes. It uses a verified subject, removes incoming Finance and other identity headers, bearer and cookie, and constructs a versioned service-authenticated Finance context. It is gated, default off, and has DEV/fixture and production-marker guards. This candidate's presence is not proof of live activation or of Finance-side network isolation. Verify the deployed route, mode, matching service proof, and downstream acceptance together. Do not treat the encoded subject as a credential.

## Login, claims and transport

Core's opt-in Identity composition hosts password and OAuth compatibility endpoints, token handling, refresh sessions and logout. The [README](../../README.md#shared-identity-auth-and-kakao-login) describes the local real-provider Kakao smoke: provider exchange and subject resolution succeeded, ending in the expected unlinked-account 409 on a clean database. It does not prove Seoul DEV login, enrollment, or Product access. A Platform account and valid credentials are distinct from Carelog profile/claims and authorization; a missing Carelog profile may prevent Carelog login despite valid shared credentials.

For the later candidate, [Core enrollment properties at `f9adfd3d`](https://github.com/ranikun-labs/platform-services/blob/f9adfd3d338f482e7c2967512522e5b4e2354619/platform-core/identity/src/main/java/com/ranikunlabs/platform/identity/adapter/enrollment/CarelogEnrollmentProperties.java) and the [Carelog rollback-window test at `f03f1788`](https://github.com/ranikun-labs/carelog-be/blob/f03f1788b036d203056bf042eed780706375858c/carelog-be/src/test/java/carelog/carelog/user/web/internal/EnrollmentRollbackWindowIntegrationTest.java) document the intended split: new enrollment uses HTTPS while the legacy HTTP claims path can remain available during rollback; TLS claims are also supported. The separate paths and flags matter during a staged rollout. These are candidate source/test observations, not proof that DEV certificates, name verification, security groups, effective URLs, or rollback window are correct. Confirm both Core-to-Carelog enrollment and claims over their effective endpoints, including trust and hostname verification, and only retire legacy HTTP after old Core rollback is no longer required. The infrastructure handoff owns exact deployment configuration and sequencing.

## Logout and AI revocation

[Identity logout](../../platform-core/identity/src/main/java/com/ranikunlabs/platform/identity/application/AuthServiceImpl.java) writes the access token to the blacklist for its remaining lifetime before deleting the refresh session. Gateway reads `blacklist:<raw JWT>`; both sides must use the same effective Valkey endpoint, database and keyspace. The [Valkey runbook](valkey-dev-clean-replacement.md) specifies the contract and verification precautions. Repository tests cover Identity's write and Gateway's rejection, but those tests do not establish a live shared keyspace or an end-to-end Seoul DEV result.

The source routes `/rag/**` through Gateway and its general protected-request filter, so a blacklisted bearer should be rejected there when that path and shared blacklist are actually used. This does not prove revocation for a direct RAG/AI endpoint, an alternate ingress, an already running request, cached work, or a separately issued credential. Verify network bypass is closed and perform an authorized DEV test: log in, exercise a protected Carelog and AI route, log out, then retry the same bearer on both routes and confirm rejection without logging the bearer. Also verify refresh cannot restore the logged-out session and test blacklist-store failure behavior. Record timestamps, image digests, routes and status outcomes only. Until this is done, live logout-to-AI revocation is unverified.
